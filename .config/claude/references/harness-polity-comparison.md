# ハーネス政体比較: Claude Code vs Codex

> 出典: wquguru/harness-books — 「殊途同归，还是各表一枝」

## 核心フレームワーク

Claude Code と Codex は同じ前提を共有する:
- モデルは不安定部品
- ハーネスが秩序の源泉
- Prompt だけでは制御できない

**分岐点は「秩序をどの層に配置するか」**。

---

## 二つの政体

### Claude Code: 実行時共和制 (Runtime Republic)

秩序は **Query Loop の現場判断** から生まれる。

| 特徴 | 実装 |
|------|------|
| **制御面** | 動的な組み立て（`systemPrompt.ts` で条件注入） |
| **連続性** | Query Loop の状態機械 (`query.ts` のターンをまたぐ状態) |
| **ローカル規則** | `CLAUDE.md` — 会話現場に読み込まれる「現場の掲示板」 |
| **ツール権限** | 現場でのオーケストレーション (`toolOrchestration.ts` の並行安全判定) |
| **強み** | 柔軟性。現場変化に即応できる |
| **弱み** | 長い会話で指示が劣化し、意味が薄まるリスク |

**比喩**: 経験から育った制御力。現場の指揮官。

### Codex: 制御面立憲制 (Constitutional Control Plane)

秩序は **構造化された fragment と policy** から生まれる。

| 特徴 | 実装 |
|------|------|
| **制御面** | Instruction Fragment (`fragment.rs` で型・境界・ラップ規則) |
| **連続性** | Thread / Rollout / State の明示的構造 |
| **ローカル規則** | `AGENTS.md` — スコープと優先度の継承関係を明示 |
| **ツール権限** | ExecPolicy (`execpolicy/src/lib.rs` で宣言的ポリシー) |
| **強み** | デバッグしやすさ。規則の由来と適用範囲が明確 |
| **弱み** | 構造維持コスト。型・マーカー・シリアライゼーションの維持が必要 |

**比喩**: 制度設計から育った制御力。制度に仕える秘書役。

---

## 委譲時の判断軸

「どちらが優れているか」ではなく「何を恐れるか」で選ぶ。

| 主要矛盾 | 推奨先 | 理由 |
|-----------|--------|------|
| 長い会話で指示が劣化する | Claude Code | runtime heartbeat が現場で指令を再構築 |
| 規則の由来・適用範囲が不明確 | Codex | fragment 化で規則が第一級オブジェクト |
| 現場変化が激しい | Claude Code | 動的な組み立てが条件注入に強い |
| 制度化・プログラム化を進めたい | Codex | 構造化 fragment → precedence/merge rule に拡張可能 |

---

## 自分のハーネスを設計するとき

1. **主要矛盾を先に決める**: 現場の制御不能 or 制度の歪み
2. **片方を先に固める**: 両方同時に進めると、どちらも中途半端になるリスクがある
3. **安定後に他方を補う**: runtime heartbeat が安定 → 構造化を追加、またはその逆

> 笼子的位置，决定了系统以后会长成什么样。
> （檻の位置が、システムが将来どう成長するかを決める）
